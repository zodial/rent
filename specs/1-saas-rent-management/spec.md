# SAAS 出租屋管理 — 验收化规范（聚焦用户价值）

## 概要
本文件以用户旅程为中心，定义每个关键功能的可测化验收标准，确保实现带来明确业务价值（可操作性、权限隔离、合同一致性、分账准确、移动端响应）。

> 技术与流程约束（必须遵守）
> - 后端：Golang（使用 Gin + GORM）
> - 前端：Vue 3 + TypeScript（优先使用原生 Web API，避免非必要第三方库）
> - 数据库：SQLite（初期）
> - 开发流程：TDD（先写失败测试），CI 在合并前强制通过测试与覆盖率（>=90%）
> - 性能：关键路径首交互目标 ≤ 100ms

## 优先用户场景与验收测试（按优先级 P1→P3）

### 场景 P1 — 超级管理员创建住宅并授权住宅管理员
- 目标价值：快速上线房源并委派本地管理，确保权限隔离。
- 验收:
  1. Given: 已登录且角色为 `SUPER_ADMIN`
     When: 提交新住宅创建请求（payload 包含 name, address, rooms[], managers: [{admin_id, equity_percent}])
     Then: API 返回 `201 Created`，响应体包含住宅 id；房间在房间列表可见；住宅详情返回 managers 列表且对应 manager 的 `equity_percent` 为 `30.0`（示例）。
  2. 权限验证：Given: 管理员 B（`PROPERTY_MANAGER`）被赋予住宅 A 的管理权限
     When: 管理员 B 访问住宅 A 的编辑接口与访问未授权住宅的编辑接口
     Then: 对授权住宅返回 `200 OK` 并允许编辑；对未授权住宅返回 `403 Forbidden`。
  3. 自动化断言：单元/集成测试覆盖住宅创建、管理员分配与占股存储（断言 DB 字段与 API 返回一致）。

### 场景 P1 — 房间办理入住与合同签订（承租人）
- 目标价值：确保租赁关系被正式记录，房间状态一致，承住人可被添加。
- 验收:
  1. Given: 房间 A1 状态为 `vacant` 且租客 C 已注册并通过认证
     When: 租客 C 发起签约请求（合同包含 room_id, tenant_id, start_date, end_date, rent_terms）并签署
     Then: API 返回 `201 Created` 合同，合同记录包含 `room_id` 与 `tenant_id`；房间 A1 状态变更为 `occupied`。
  2. 承住人添加：Given: 合同生效且租客 C 为承租人
     When: C 提交承住人 D 的信息（name, contact 等）
     Then: API 返回 `201 Created` 承住人记录；在房间居民列表查询时能看到 D（关联 tenant_id）。
  3. 自动化断言：契约状态机测试（未签→已签→可添加承住人），集成测试验证关系完整性与状态变更。

### 场景 P1 — 收入分成结算与报表生成
- 目标价值：按占股准确分配收入并生成可导出的报表供财务审核。
- 验收:
  1. Given: 合同在结算周期内产生应收租金 `1000.00`，住宅管理员 B 占股 30%（其余由其他管理员分配）
     When: 触发结算任务（手动或定时）
     Then: 生成 Transaction/allocations，其中管理员 B 的分成为 `300.00`（四舍五入规则见开放问题 Q2）；报表导出包含明细与总计且与交易表一致。
  2. 数值精度：单位测试覆盖分成算法，误差 ≤ `0.01`。
  3. 自动化断言：分成计算单测、导出 CSV/JSON 一致性测试。

### 场景 P1 — 后台关键页面首交互性能（移动端）
- 目标价值：移动端后台操作流畅，关键路径响应≤100ms 提升用户体验。
- 验收:
  1. Given: 模拟或真实移动网络与设备基线（在 CI 中采用可重复的 headless/instrumented 测试）
     When: 打开房间列表页面的首交互（首个可操作元素可见/可点）
     Then: 自动化性能测试测得中位数响应时间 ≤ `100ms`（或相对基线不退化），且在 PR 中附基准比对结果。
  2. 自动化断言：性能测试脚本（headless + instrument）在 CI 运行并在报告中通过阈值校验。

### 场景 P2 — 管理员多对多与占股编辑
- 目标价值：灵活授权与收益分配调整。
- 验收:
  1. Given: 住宅 A 已有多名管理员与占股记录
     When: `SUPER_ADMIN` 修改管理员 C 的占股为 `15.0` 并保存
     Then: DB 更新占股字段；当占股总和超出 100%（若规则限制为 100%）时，接口返回 `400 Bad Request` 并带错误信息。
  2. 自动化断言：占股校验单元测试、权限控制测试（只有 `SUPER_ADMIN` 或具备相应权限的用户可修改占股）。

### 场景 P2 — 审计日志与可追溯操作
- 目标价值：关键操作可审计以支持合规与问题追踪。
- 验收:
  1. Given: 任一用户执行关键 CRUD（如合同签订、占股修改）
     When: 操作完成
     Then: 在审计表产生一条记录：{actor_id, action, target_type, target_id, timestamp, diff}，且可通过审计 API 查询到最近 N 条记录。
  2. 自动化断言：审计生成测试、审计查询接口返回结构化日志。

### 场景 P3 — 住宅/房间基本 CRUD（移动端管理）
- 目标价值：基础管理流程无障碍。
- 验收:
  1. Given: 有权限的管理员
     When: 创建/编辑/删除房间和住宅
     Then: 各操作返回 `200/201/204` 并可在列表中反映变更；移动端界面在小屏幕上正确展示字段与操作按钮。
  2. 自动化断言：接口 CRUD 测试与基础 UI 快照/断言。

## 功能性需求与明确验收标准

### FR-1 管理员角色与权限
- FR-1.1: 支持 `SUPER_ADMIN` 与 `PROPERTY_MANAGER` 角色；所有涉及数据修改的接口强制 RBAC 校验。
  - 验收: 单元/集成测试覆盖每个接口的角色访问矩阵，确保非法访问返回 `403`。
- FR-1.2: 管理员 ↔ 住宅 为多对多关系，且每条关联记录包含 `equity_percent: decimal`。
  - 验收: CRUD API tests 验证关联创建/查询/更新，断言 `equity_percent` 存储精度与返回一致。
- FR-1.3: 只有拥有对应权限的管理员可管理其关联住宅（除 `SUPER_ADMIN`）。
  - 验收: 权限边界测试（授权访问 `200`，未授权 `403`）。

### FR-2 住宅与房间管理
- FR-2.1: 住宅与房间支持完整 CRUD，房间具备 `number, area, rent, status` 字段。
  - 验收: API CRUD 测试（端点返回码、字段校验、DB 状态一致）。
- FR-2.2: 房间状态机（`vacant`→`occupied`→`maintenance`）在合同生命周期中自动变更。
  - 验收: 合同创建/结束触发状态变更的集成测试。

### FR-3 租客、合同与承住人
- FR-3.1: 合同记录 `room_id, tenant_id, start_date, end_date, rent_terms, status`；签约后房间状态为 `occupied`。
  - 验收: 合同创建 API 返回 `201` 且 DB 与房间状态一致，相关单元测试与集成测试通过。
- FR-3.2: 签约承租人可为合同添加承住人（多条记录），承住人不会改变合同主责任人。
  - 验收: 添加承住人接口测试（关系完整性、删除/查询）。

### FR-4 收入分成与结算
- FR-4.1: 系统按合同周期计算应收并按每个管理员 `equity_percent` 分配收入（保留两位小数或另行指定）。
  - 验收: 单元测试覆盖分成算法（样例数据断言误差 ≤ `0.01`）；结算任务在测试环境可复现并生成 allocations。
- FR-4.2: 支持生成与导出分成报表（CSV/JSON），并包含明细与汇总。
  - 验收: 报表导出接口返回可解析文件并与 transactions 表一致。

### FR-5 移动优先 UI 与性能门槛
- FR-5.1: 关键管理流程在移动端可完成，首交互时间目标 ≤ `100ms`（或在 CI 性能套件中通过相对基线）。
  - 验收: CI 性能断言脚本在 PR 中运行并通过阈值，报告附带基线对比。
- FR-5.2: 前端尽量使用原生 Web API，避免非必要依赖。
  - 验收: 依赖清单在 PR 中列出且评审通过。

### FR-6 可观测性与审计
- FR-6.1: 所有关键变更产生结构化审计日志并可查询。
  - 验收: 审计生成测试、审计查询接口返回符合 schema 的记录。
- FR-6.2: 关键错误写入结构化日志并上报监控指标（或模拟上报）。
  - 验收: 日志与指标收集单元测试或集成验证。

## 成功准则（可测化）
- S1: 管理员在移动端能完成住宅/房间生命周期管理并通过权限单测验证（自动化通过率 100% 对应测试集）。
- S2: 合同签订流程在集成测试中能使房间状态一致且承住人能被添加（断言 DB 关联）。
- S3: 分成计算误差 ≤ `0.01`，报表导出与账目一致（单元/集成断言）。
- S4: 关键页面首交互中位数响应 ≤ `100ms`（或相对基线不退化），CI 性能检查通过。
- S5: 自动化测试覆盖率 ≥ `90%`（CI 强制），PR 提交必须包含覆盖率报告。

## 边界条件与错误场景（均需测试）
- 房间重复签约尝试应返回 `409 Conflict` 并保留原合同。
- 管理员占股总和超出允许上限时应拒绝并返回明确错误。
- 合同期冲突（重叠时间段）在签约时被拒绝或提示（由业务规则决定并实现测试）。

## 可测性说明（TDD 要求）
- 每个验收场景必须对应至少一个自动化测试用例（单元或集成）。
- 所有业务关键点（权限、合同状态机、分成算法、审计）先写失败测试再实现。
- CI 在合并前强制运行测试、覆盖率与性能检查。

## 开放问题
- Q1: 系统是否需要原生多租户隔离（每租户独立 DB）还是单实例多租户？（影响 DB 模型与权限边界）
- Q2: 收入分成结算的四舍五入与精度规则（例如保留两位小数，或按分/厘精度）？
- Q3: 是否需要内置支付/结算通道（自动转账），或仅生成分成报表供手动结算？
